# 部署与运维

> 面向「要发版 / 要排障」的场景。架构背景见 `docs/架构说明.md`，
> 服务器侧的目录与容器约定见 `deploy/README.md`。

## 一、生产拓扑

| 组件 | 位置 | 对外地址 |
|---|---|---|
| 认证中心 | 容器 `idp_auth_server`，`127.0.0.1:18090 → 8080` | `https://idp.civer.cn` |
| 管理端 API | 容器 `idp_user_manage`，`127.0.0.1:18082 → 8081` | `https://um.civer.cn` |
| 管理端前端 | EdgeOne Pages 项目 `aidp-admin-console` | `https://admin.civer.cn` |
| 数据库 | 1Panel PostgreSQL，库 `idp_auth_db` | 内网 |
| 缓存/会话 | 1Panel Redis | 内网 |

jar 由 1Panel「Java 运行环境」托管：`/home/idp/*` 挂载到容器 `/app`，`run.sh` 执行 `java -jar`。

## 二、环境变量

改 `/opt/1panel/runtime/java/idp_*/.env` 后 `docker restart` 生效，**不需要重新构建 jar**。

**auth-server**

| 变量 | 作用 | 生产值 |
|---|---|---|
| `APP_BASE_URL` | 决定 OIDC `issuer`，必须是对外地址 | `https://idp.civer.cn` |
| `INITIAL_CLIENT_SECRET` | 初始客户端密钥，须与管理端 `CLIENT_SECRET` 一致 | 从密钥管理取 |
| `FLYWAY_ENABLED` | 是否执行库迁移 | `true` |
| `SESSION_STORE` / `CACHE_TYPE` | 单机留空，多实例设 `redis` | `redis` |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | Redis 连接 | 按实际 |

**user-manage**

| 变量 | 作用 | 生产值 |
|---|---|---|
| `APP_AUTH_SERVER_URL` | OIDC 发现 + 登录跳转，必须是公网地址 | `https://idp.civer.cn` |
| `APP_AUTH_SERVER_API_URL` | 转发调用地址，可指向容器内网绕开公网 CDN | 可选，默认回落到上一项 |
| `APP_BASE_URL` | 本服务对外地址（拼回调地址） | `https://um.civer.cn` |
| `FRONTEND_URL` | 登录成功/失败回跳的前端地址 | `https://admin.civer.cn` |
| `CORS_ALLOWED_ORIGINS` | 允许的前端来源，逗号分隔 | `https://admin.civer.cn` |
| `COOKIE_SAME_SITE` / `COOKIE_SECURE` | 跨站部署需 `None` + `true` | `None` / `true` |
| `CLIENT_SECRET` | 必须与认证中心侧一致 | 从密钥管理取 |
| `SESSION_STORE` / `REDIS_*` | 同上 | `redis` |

> 只改 `APP_BASE_URL` 而不同步更新各客户端 `issuer-uri`，会导致 Back-Channel 验签失败
> （现象：全局登出时其它系统不退）。改域名是联动操作，见下节清单。

## 三、本地构建与自测

```bash
# 认证中心（含 14 个回归测试）
mvn clean package

# 管理端后端
cd client-usermanage && mvn clean package

# 前端（产物在 frontend/dist，构建参数已固化在 .env.production）
cd client-usermanage/frontend && pnpm install --ignore-scripts && pnpm build
```

`pnpm install` 必须带 `--ignore-scripts`：pnpm 10+ 会拦截 esbuild 的安装脚本并直接失败，
而 esbuild 的二进制来自平台可选依赖，跳过脚本不影响构建。

## 四、发布通路

```
本地 commit
  → git push origin main / git push origin <tag>
    → GitHub Actions「Sync to CNB」（.github/workflows/sync-cnb.yml）
      → CNB 仓库收到 tag
        → CNB 流水线（.cnb.yml），按 tag 前缀分流
          → 构建依赖缓存镜像 → 测试 + 构建 + 发布制品 → rsync → 重启 → 健康校验
```

**标签即发布开关**，前缀决定发哪个服务：

| 标签 | 服务 | 触发流水线 |
|---|---|---|
| `auth-v2.3.9` | 认证中心 | `auth-v*` |
| `user-v2.3.9` | 管理端后端 | `user-v*` |
| 其它（如 `v1.2.3`） | —— | 不触发，**不会发布** |

版本号必须三段式（`X.Y.Z`），否则构建阶段第一行就报错退出。

### 每个环节怎么确认它成了

| 环节 | 确认方式 |
|---|---|
| GitHub → CNB（标签） | GitHub 仓库 Actions 页面对应 run 的「1) 同步标签」步为绿色 |
| GitHub → CNB（分支） | 同上「2) 同步分支」步；`git ls-remote --heads cnb` 与 `origin` 一致 |
| CNB 构建 | CNB 流水线详情：阶段 2 结束能看到 `BUILD SUCCESS` 与 `Auth-Server.jar` |
| CNB 制品 | `https://maven.cnb.cool/civer/cnb-maven/-/packages/` 有对应版本 |
| 部署 | 阶段 3 日志末尾 `health UP http://127.0.0.1:18090/actuator/health` |

### 日常发版

```bash
git tag auth-v2.3.9 && git push origin auth-v2.3.9     # 只发认证中心
git tag user-v2.3.9 && git push origin user-v2.3.9     # 只发管理端后端
```

两个服务同时改动就推两个标签。**前端不在这条链路里**，见第六节。

构建阶段会跑完整测试（14 个），测试不过就不会产出 jar、也不会部署。
制品推送 CNB Maven 库是「尽力而为」：同版本不允许重复发布，重跑旧标签做回滚时
这一步会失败并自动退回本地构建，不影响部署。

## 五、镜像同步故障：`non-fast-forward`

这是本链路唯一一次真正断掉的原因，务必认识它。

**现象**：GitHub Actions 的 `Sync to CNB` 连续失败，日志里是

```
! [rejected]  main -> main (non-fast-forward)
error: failed to push some refs to 'https://cnb.cool/civer/Quisperc/AIDP.git'
```

**根因**：CNB 侧的 `main` 有 GitHub 没有的提交（历史被重写过、或有人在 CNB 上直接提交），
两边分叉，普通 push 拒绝。

**后果**：旧版 workflow 把「推分支」和「推标签」放在同一步，分支一失败整步退出，
**标签也永远不会推到 CNB**，于是没有任何发布发生——而且 GitHub 只是把 run 标红，
很容易被忽略。

**现在的防护**：workflow 拆成两步，标签先推、分支后推。分支再分叉也只影响镜像完整性，
不会阻断版本发布；同时分支失败仍然是红灯，不会被掩盖。

**一次性修复分叉**（确认 CNB 侧没有需要保留的提交后执行）：

```bash
git fetch origin
git push cnb origin/main:main --force      # 以 GitHub 为准重置 CNB 的 main
```

复核：

```bash
git ls-remote --heads origin main
git ls-remote --heads cnb main            # 两个 SHA 应一致
```

之后重新推一次 workflow（`Actions → Sync to CNB → Run workflow`）确认变绿。

> 预防：在 CNB 仓库设置里把 `main` 设为保护分支，禁止直接推送与在线编辑，
> 让它只作为 GitHub 的只读镜像。

## 六、前端发布（EdgeOne Pages）

前端不在 CNB 流水线内，必须手工发。**构建参数已固化在
`client-usermanage/frontend/.env.production`**，不再依赖命令行 export。

```bash
cd client-usermanage/frontend
pnpm install --ignore-scripts
pnpm build                     # 产物在 dist/
cp dist/index.html dist/404.html   # SPA 路由回退

cd ..
rm -rf pages-out && mkdir pages-out && cp -r frontend/dist/. pages-out/
# EdgeOne 部署时 workspacePath 与 builtFolderPath 必须都指向 pages-out 这个纯产物目录
```

部署后必须验两条，缺一不可：

```bash
curl -s https://admin.civer.cn/ | grep -oE 'assets/index-[A-Za-z0-9_-]+\.js'
curl -s https://admin.civer.cn/<上面那条 JS 路径> | grep -o 'https://um.civer.cn'
```

第二条没输出，说明部署的是「API 基址为空」的旧产物，前端会去请求自己的域名并被
SPA 回退返回 index.html，浏览器报 `Unexpected token '<'`。

## 七、发布后验证清单

- [ ] `https://idp.civer.cn/.well-known/openid-configuration` 的 `issuer` 正确
- [ ] `https://idp.civer.cn/actuator/health` 返回 `UP`
- [ ] `https://um.civer.cn/actuator/health` 返回 `UP`（含 Redis 探针）
- [ ] `https://um.civer.cn/api/me` 未登录返回 **401**（而不是 HTML 登录页）
- [ ] 浏览器完整走一遍：登录 → 用户列表 → 客户端管理 → 修改资料 → 退出
- [ ] 退出后另一个子系统的会话也被清掉（验证 Back-Channel 广播）
- [ ] 容器日志无 `ERROR`：`docker logs --tail 200 idp_auth_server`

## 八、回滚

```bash
# 方式 A：重新发布上一个标签（推荐，可追溯）
git push origin :refs/tags/auth-v2.3.8     # 删除已存在标签
git tag auth-v2.3.8 <上一个 commit>         # 重建
git push origin refs/tags/auth-v2.3.8      # 重新触发构建与发布
```

方式 B（手工替换 jar + 重启）与更完整的说明见 `deploy/README.md` 第五节。

> 流水线目前不保留历史 jar，回滚必然要重跑一次构建。若要实现真正的一键回滚，
> 需要把服务器上的 `Auth-Server.jar` 改成指向 `releases/<version>/` 的软链，
> 属于运维改造，尚未执行。
