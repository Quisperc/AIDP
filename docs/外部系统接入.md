# 外部系统接入：获取 OIDC 配置

> 面向**不在本仓库里**的系统（Node / Python / Go / PHP / 桌面端 / 另一个团队的 Java 服务）。
> 你需要的所有端点都能从认证中心自动发现，**不要手工抄写或猜测地址**。
> 端点取自生产环境实测（2026-11-04）；scope 与 claim 部分按 2026-11 Dev 规范化版本描述。

---

## 一、只需要记住一个地址：issuer

```
https://idp.civer.cn
```

`issuer` 是 OIDC 的唯一入口，其余端点都是它的派生。**必须逐字符一致**：
末尾多一个 `/`、写成 `http://`、写成内网地址，都会让 token 校验的 `iss` 比对失败。

---

## 二、拿到完整配置的三种方式

### 方式 1：浏览器直接看

打开：

```
https://idp.civer.cn/.well-known/openid-configuration
```

返回一段 JSON，这就是 **OIDC Discovery 文档**，也是各语言 SDK 唯一会读的东西。

### 方式 2：命令行提取关键字段

```bash
curl -s https://idp.civer.cn/.well-known/openid-configuration \
  | python -m json.tool | head -40
```

只想看端点：

```bash
curl -s https://idp.civer.cn/.well-known/openid-configuration \
  | python -c "import json,sys; d=json.load(sys.stdin); [print(f'{k:28} {v}') for k,v in d.items() if k.endswith('_endpoint') or k in ('issuer','jwks_uri')]"
```

实测输出（生产）：

| 字段 | 值 |
|---|---|
| `issuer` | `https://idp.civer.cn` |
| `authorization_endpoint` | `https://idp.civer.cn/oauth2/authorize` |
| `token_endpoint` | `https://idp.civer.cn/oauth2/token` |
| `jwks_uri` | `https://idp.civer.cn/oauth2/jwks` |
| `userinfo_endpoint` | `https://idp.civer.cn/userinfo` |
| `end_session_endpoint` | `https://idp.civer.cn/connect/logout` |
| `revocation_endpoint` | `https://idp.civer.cn/oauth2/revoke` |
| `introspection_endpoint` | `https://idp.civer.cn/oauth2/introspect` |

其他关键能力：

- `response_types_supported`: `["code"]` —— 只支持授权码模式，没有 implicit
- `grant_types_supported`: `authorization_code`、`refresh_token`、`client_credentials`（本中心注册的客户端只开放前两者）
- `code_challenge_methods_supported`: `["S256"]` —— PKCE 只接受 S256，不接受 `plain`
- `id_token_signing_alg_values_supported`: `["RS256"]`
- `scopes_supported`: `["openid", "profile", "email"]` —— 三者均已为客户端注册，可显式请求
- `sub` 是**不可变 UUID**（`users.public_id`），不是用户名。客户端必须按 `(iss, sub)` 关联本地账号：
  用户改登录名后 `sub` 不变。`email` / `preferred_username` 不能当唯一标识（OIDC Core 明确禁止）。
- `email` 仅在请求了 `email` scope 时返回，并附 `email_verified`；自助填写的邮箱为 `false`，
  不得据此自动合并账号。`nickname` / `preferred_username` 属于 `profile` scope。

### 方式 3：只把 issuer 交给 SDK（推荐）

绝大多数库支持「给 issuer，自动拉 discovery」：

```javascript
// Node.js · openid-client v6
import * as client from 'openid-client';
const config = await client.discovery(
  new URL('https://idp.civer.cn'),
  process.env.OIDC_CLIENT_ID,
  process.env.OIDC_CLIENT_SECRET,
);
```

```python
# Python · authlib
from authlib.integrations.requests_client import OAuth2Session
# 或用 requests 先取 discovery：requests.get(ISSUER + '/.well-known/openid-configuration').json()
```

```go
// Go · go-oidc
provider, err := oidc.NewProvider(ctx, "https://idp.civer.cn")
// provider.Endpoint() / provider.Verifier() / provider.UserInfo()
```

```java
// Spring Boot（外部服务侧）
spring:
  security:
    oauth2:
      client:
        provider:
          aidp:
            issuer-uri: https://idp.civer.cn
```

## 三、光有端点还不够：先注册客户端

本中心**不支持动态注册**（discovery 里没有 `registration_endpoint`），
`client_id` / `client_secret` 必须由管理员在管理台创建后线下交付：

1. 管理员登录 `https://idp.civer.cn/admin/clients` → 「注册客户端」
2. 填入：
   - `Client ID`：全局唯一，建议与系统同名，如 `report-portal`
   - `Client Secret`：随机长串（建议 32 位以上）
   - `Redirect URI`：**精确到协议、域名、端口、路径、查询参数**，如
     `https://report.civer.cn/login/oauth2/code/aidp`
   - `Post Logout Redirect URI`：如 `https://report.civer.cn/login`
   - 要求 PKCE：保持勾选
3. 把 `client_id` / `client_secret` 通过环境变量注入你的服务（**不要进仓库**）

> 回调地址只要与注册值差一个字符，授权请求就会被拒绝。多个环境（测试/生产）分别注册，不要共用一个客户端。

## 四、最小接入流程（授权码 + PKCE）

### 1. 发起授权

浏览器跳转（注意 `state` 与 `code_challenge`）：

```
https://idp.civer.cn/oauth2/authorize
  ?response_type=code
  &client_id=report-portal
  &redirect_uri=https%3A%2F%2Freport.civer.cn%2Fcallback
  &scope=openid%20profile%20email
  &state=<随机串，回调时要原样比对>
  &nonce=<随机串，会写进 id_token，用来防重放>
  &code_challenge=<BASE64URL(SHA256(code_verifier))>
  &code_challenge_method=S256
```

用户登录并同意后，浏览器回到 `redirect_uri?code=...&state=...`。**先比对 `state`**，再换 token。

### 2. 用 code 换 token

```bash
curl -s -X POST https://idp.civer.cn/oauth2/token \
  -u "$OIDC_CLIENT_ID:$OIDC_CLIENT_SECRET" \
  -d grant_type=authorization_code \
  -d code="$CODE" \
  -d redirect_uri="https://report.civer.cn/callback" \
  -d code_verifier="$CODE_VERIFIER"
```

返回 `access_token` / `id_token` / `refresh_token`（`token_type: Bearer`）。

客户端认证支持两种：HTTP Basic（`-u`，推荐）或表单里带 `client_id`/`client_secret`。
用错会得到 `401 {"error":"invalid_client"}`。

### 3. 校验 id_token（不要「解出 payload 就信」）

必须逐项检查：

| 校验项 | 期望 |
|---|---|
| 签名 | RS256，用 `jwks_uri` 的公钥验，`kid` 对应即可 |
| `iss` | 严格等于 `https://idp.civer.cn` |
| `sub` | 不可变 UUID，作为本地账号主键；改名不会变化，不要用 username/email 代替 |
| `aud` | 等于你的 `client_id` |
| `exp` / `iat` | 未过期；允许少量时钟偏差（建议 ≤60s） |
| `nonce` | 等于发起授权时生成的值 |
| `azp` | 多 audience 场景下等于 `client_id` |

公钥可带缓存地拉取：

```bash
curl -s https://idp.civer.cn/oauth2/jwks | python -m json.tool | head -12
```

### 4. 取用户信息（可选）

```bash
curl -s https://idp.civer.cn/userinfo -H "Authorization: Bearer $ACCESS_TOKEN"
```

### 5. 退出（全部是标准端点）

认证中心**没有**自研的登出/撤销接口，只有下面三种标准做法：

| 你要做的事 | 用什么 | 谁发起 |
|---|---|---|
| 只退出本应用 | 清你自己的本地会话即可，IdP 完全不用参与 | 你的后端 |
| 退出本应用 + 作废它的令牌 | `POST /oauth2/revoke`（RFC 7009），带 `client_id`/`client_secret` 与 `token` | 你的后端 |
| 让用户从 AIDP 全局退出 | 跳到 `end_session_endpoint` = `https://idp.civer.cn/connect/logout`，带 `id_token_hint` 与已注册的 `post_logout_redirect_uri` | 浏览器 |

说明：

- 「退出某个应用」**不需要**通知 IdP。以前文档让子系统把浏览器踢到认证中心去撤销同意，
  那是自研端点时代的做法；现在该端点已删除。清掉本地会话即完成退出，
  IdP 保留同意记录反而让用户下次免于再点一次同意。
- 真正需要「让这个应用的令牌立即失效」时，走 RFC 7009 的撤销端点，这是后端的 POST，
  不需要浏览器跳转。
- 全局退出会删除该用户的**全部**同意与已签发令牌。各子系统的本地会话由应用自行按
  RP-Initiated Logout 结束，或随 access token 失效自然退出；认证中心不推送私有登出消息。
  这是唯一会动 consent 的入口。

## 五、不依赖任何 SDK 的最小验证（5 分钟）

```bash
ISSUER=https://idp.civer.cn

# 1. discovery 可达
curl -sf "$ISSUER/.well-known/openid-configuration" | grep -o '"issuer":"[^"]*"'

# 2. 公钥可达（至少 1 把 RSA key）
curl -sf "$ISSUER/oauth2/jwks" | grep -o '"kid":"[^"]*"'

# 3. token 端点在线（预期 401 invalid_client，说明端点活着且要求凭证）
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$ISSUER/oauth2/token" \
  -d grant_type=authorization_code -d code=x -d redirect_uri=https://example.com/cb \
  -u nope:nope

# 4. 登录页可达（预期 200）
curl -s -o /dev/null -w "%{http_code}\n" "$ISSUER/login"
```

四条都符合预期，说明网络与端点侧没问题，剩下的就是客户端参数。

## 六、常见坑

| 现象 | 原因 |
|---|---|
| `invalid_client` | secret 错，或用了不匹配的认证方式（Basic vs POST），或客户端只注册了 `client_secret_basic` |
| `invalid_grant` | code 过期（一次性，约 5 分钟）、`redirect_uri` 与授权时不一致、`code_verifier` 与 challenge 不匹配 |
| 授权页直接报「客户端未在认证中心注册」 | `client_id` 拼错，或该客户端已被删除 |
| 回调 400 `invalid_request` | 注册的回调地址与实际请求不完全一致（含端口、末尾 `/`、查询串） |
| id_token 验签失败 | `iss` 与 `issuer` 不完全一致；或服务端缓存了旧 JWKS（密钥轮换后需刷新） |
| userinfo 里没有昵称/邮箱 | claim 按 scope 返回：昵称需 `profile`、邮箱需 `email`。请求写成 `scope=openid profile email`，客户端需已注册这三个 scope |
| 从内网调用超时 | 认证中心只开放在 `https://idp.civer.cn`（宿主 `127.0.0.1:18090`），内网直连需自行打通，不要改 issuer |

## 七、安全检查清单

- [ ] 全程 HTTPS，回调地址也是 HTTPS
- [ ] `state` 与 `nonce` 每次随机，回调时校验
- [ ] PKCE 用 S256
- [ ] `client_secret` 走环境变量/密钥管理，不写进代码与镜像
- [ ] id_token 校验签名 + `iss` + `aud` + `exp` + `nonce`，不信任未验签的 payload
- [ ] 日志里不打印 `access_token` / `refresh_token` / `client_secret`
