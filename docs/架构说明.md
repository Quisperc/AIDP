# 架构说明

> 讲清楚三件事：系统由哪些部分组成、登录/退出两条主链路怎么走、为什么这么设计。

## 一、模块与边界

| 模块 | 端口 | 角色 | 是否持有数据 |
|---|---|---|---|
| `auth-server`（根目录） | 8080 | OIDC 提供方 + 资源服务器 | 是，PostgreSQL 唯一写入方 |
| `client-usermanage`（后端） | 8081 | 管理端 REST API | 否，纯转发 |
| `client-usermanage/frontend` | — | Vue 3 管理后台 SPA | 否，部署在 EdgeOne Pages |
| 第三方子系统 | 各自 | OIDC 客户端 | 各自业务库，不碰认证库 |

**一条硬边界：只有 `auth-server` 访问认证数据库。**

管理端完全不知道表结构，它的 `/admin/**` 接口只是把请求带上用户令牌转发给认证中心的
`/api/**`。这个决定的收益是数据一致性只有一个入口（客户端注册、用户、consent 都由
`ClientService` / `UserAdminService` 收口），代价是链路变长：

```
浏览器 ──(会话 Cookie)──> 8081 ──(Bearer 令牌)──> 8080 ──> PostgreSQL
```

因此管理端必须解决「令牌从哪来」：OIDC 登录后 `OAuth2AuthorizedClient` 由
`RedisOAuth2AuthorizedClientService` 存在 Redis（`SESSION_STORE=redis` 时），
`AuthServerHttpClientConfig` 的拦截器在每次转发时取出并注入 `Authorization` 头。

> 备选方案（管理端直连数据库）评估过：能砍掉令牌转发这一层，但会让两个应用各自
> 维护一套事务与校验逻辑，最终没有采用。原始评估见 `docs/archive/`。

## 二、登录链路（Authorization Code + PKCE）

1. 用户访问管理端 → 前端拿不到 `/api/me` 的 200 → 跳
   `{idp}/oauth2/authorization/oidc-client?redirect=<前端完整 URL>`
2. `auth-server` 若未登录，展示登录页（Thymeleaf，服务端渲染）
3. 已登录但未授权 → 展示同意页 `/oauth2/consent`，确认后写入 `oauth2_authorization_consent`
4. 回调 `{um}/login/oauth2/code/oidc-client`，后端用 code + secret 换 token
5. `SecurityConfig.oidcUserService()` 把 ID Token 里的 `roles` 映射成 `ROLE_*` 权限
6. 建立本地会话（Cookie 名 `CLIENT_SESSIONID`），重定向到 `redirect` 参数指定的地址
7. 前端拿到 200 后进入页面；后续业务请求靠 Cookie + `X-XSRF-TOKEN` 头

`roles` claim 由 `TokenConfig.jwtTokenCustomizer()` 写入，**两个方向都要接**：

- 认证中心侧 `jwtAuthenticationConverter()` 把 claim 还原成 authority，否则 `/api/**` 一律 403；
- 客户端侧 `oidcUserService()` 做同样的映射，否则 `/admin/**` 一律 403。

这两处历史上都漏接过，排查过程见 `docs/故障复盘.md`。

## 三、退出链路（两档）

**A. 全局退出（`{idp}/oauth2/logout-all`）**

1. 清除 SSO 会话与 `oauth2_authorization_consent`
2. `SsoLogoutService` 遍历所有客户端的 `redirect_uris`，按 `host:port` 拼出
   `/api/sso-logout`，用认证中心私钥签一个 `logout_token`（JWT）POST 过去
3. 各子系统用 `/oauth2/jwks` 验签，校验 `aud` / `iss`，再按 principal 精确失效本地会话
4. 浏览器回到 `redirect_uri`（必须命中已注册 host 白名单，防开放重定向）

**B. 单点退出（只退当前子系统）**

清本地会话 + 跳 `{idp}/oauth2/revoke-consent?client_id=...`，只删当前客户端的 consent，
SSO 会话保留，其它子系统不受影响。

> 广播是 `sendAsync` 异步的：连接超时 3 秒、单请求超时 5 秒、固定 4 个守护线程。
> 对端不响应只打 WARN，不会拖住登出请求。

## 四、密钥、会话与缓存

| 关注点 | 单机默认 | 多实例（`SESSION_STORE=redis`） |
|---|---|---|
| JWT 签名密钥 | `oauth2_signing_key` 表（Flyway 建表，启动时读取或生成） | 同左，全实例共享同一把 |
| HTTP Session | Servlet 容器本地 | Redis（`aidp:auth` / `aidp:admin` 命名空间） |
| SessionRegistry | `SessionRegistryImpl`（内存） | `SpringSessionBackedSessionRegistry` |
| 登出白名单缓存 | ConcurrentMap | RedisCacheManager（任一实例 clear 全体可见） |
| OAuth2 令牌（管理端） | InMemory | Redis Hash，跨重启存活 |

**签名密钥落库**是这轮最关键的结构性修复：原先每次启动随机生成，导致「重启即全员掉线」
且多实例互相验不了签，架构上锁死单实例。密钥损坏时启动直接失败，不静默重建
（静默重建会让已签发的令牌全部作废）。

## 五、开启多实例

两个模块都要设置，删掉即回到单机，无需改代码：

```bash
SESSION_STORE=redis
CACHE_TYPE=redis
REDIS_HOST=<redis>
REDIS_PORT=6379
REDIS_PASSWORD=<password>
```

管理端额外依赖 `repository-type: indexed`（已固定在 `application.yml`）：它才会创建
`FindByIndexNameSessionRepository`，`SpringSessionBackedSessionRegistry` 靠它按用户名
查会话，否则 `maximumSessions(1)` 形同虚设。

Redis 若禁用 `CONFIG` 命令，把 `spring.session.redis.configure-action` 改成 `none`，
并手动设置 `notify-keyspace-events Egx`。不配置只影响会话过期事件，不影响读写。

`oauth2_signing_key` 由 Flyway 建立，首次启动的实例生成密钥，其余实例复用（并发启动已处理）。
**所有实例必须连同一个库**，否则 `iss` 与密钥不一致，Back-Channel 验签必然失败。

## 六、已知取舍与技术债

| 项 | 现状 | 影响 | 备注 |
|---|---|---|---|
| 管理端令牌不自动刷新 | 直接取 `OAuth2AuthorizedClient`，不走刷新流程 | access token（30 分钟）过期后转发调用返回 401 | 前端 `http.ts` 捕获 401 自动重走 SSO，用户无感；彻底解决需引入 `OAuth2AuthorizedClientManager` |
| `DELETE /api/users/{id}` 实为停用 | `UserAdminService.disable()` 只置 `enabled=false` | 语义与 HTTP 动词不符 | 刻意保留授权与审计痕迹，调用方不要指望真的删记录 |
| `PUT /api/users/{id}` 的 `enabled` 是原始类型 | 请求体省略该字段会被当成 `false` | 管理端表单始终全量提交，暂无问题 | 若改部分更新，需换成 `Boolean` 三态 |
| 流水线不保留历史 jar | rsync 直接覆盖 | 回滚要重新发布旧标签 | 见 `deploy/README.md` 第五节 |
| 前端未纳入自动发布 | EdgeOne Pages 手工部署 | 改前端不随 tag 自动上线 | 构建参数已固化在 `.env.production`，步骤见 `docs/部署与运维.md` |
| 认证中心页面是 Thymeleaf | 登录/同意/错误页服务端渲染 | 无法 SPA 化 | OAuth2 要求用户代理与授权服务器同源交互，这是正确做法，不算债 |
