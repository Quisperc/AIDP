## 九、管理接口 500 的根因与修复（2026-11-03 晚）

现象：admin.civer.cn 前端正常，但 `/admin/users`、`/admin/clients` 全部 500。

根因链条：

1. Spring Security 对**已认证**用户默认把 `OAuth2AuthorizedClient`（access/refresh
   token）存在应用级 `InMemoryOAuth2AuthorizedClientService`，**不在 HttpSession 里**。
   所以 Redis 会话中能看到 `SPRING_SECURITY_CONTEXT`，却看不到任何 authorized client。
2. 本轮把 Session 放进 Redis 后，重启管理端容器只会清空应用内存里的 token，
   而 Redis 里的会话还在 —— 用户「看起来仍登录」，服务端却拿不到 token。
3. 转发调用认证中心 `/api/users` 时没有 Authorization 头 → 401，
   异常直接冒泡到 DispatcherServlet → 前端看到 500。

三层修复：

- **持久化令牌**：`RedisOAuth2AuthorizedClientService`（仅 SESSION_STORE=redis 时启用）
  把 token 拆成字符串字段存 Redis Hash，读取时用 ClientRegistrationRepository
  重新组装 `OAuth2AuthorizedClient`。不序列化整个对象图，跨重启存活。
  注意 Spring Security 7 起 `OAuth2AuthorizedClient` 已是具体类，
  `DefaultOAuth2AuthorizedClient` 已移除。
- **正确取用令牌**：`AuthServerHttpClientConfig` 改用
  `OAuth2AuthorizedClientManager.authorize()`（从 repository 加载 + 过期自动刷新），
  不再直接用 `OAuth2AuthorizedClientService.loadAuthorizedClient()`。
  同时新增 `app.auth-server-api-url`，可让转发调用走容器内网，绕开公网 CDN。
- **兜底**：`ClientApiExceptionHandler` 把下游 401/403/409 映射成明确状态与中文提示，
  不再一律 500；前端 `http.ts` 在业务接口 401 时自动重新走一次 SSO。

因此**首次刷新页面会自动重新登录一次**（把 token 写进 Redis），之后重启应用不再掉线。
验证方式：登录后查 Redis 应出现 `aidp:oauth2:authorized:*` 键，且管理接口返回 200。

## 十一、403 根因：JWT roles claim 未被消费

现象：500 修好后 `/admin/users`、`/admin/clients` 变成 403。

排查结论（用 Redis 中的真实 token 直连验证）：

| 请求 | 状态 |
|---|---|
| 无 token 调 /api/users | 401 |
| 带有效 token 调 /api/users | **403** |
| token payload | `roles: [ROLE_ADMIN]`、`scope: [openid, profile]`、`iss` 正确、未过期 |

`TokenConfig.jwtTokenCustomizer()` 已经把用户角色写进 `roles` claim，
但 `.oauth2ResourceServer(jwt(withDefaults()))` 用的是默认
`JwtAuthenticationConverter` —— 它只把 `scope`/`scp` 转成 `SCOPE_*` authorities，
**完全忽略 roles**。于是 token 里带着 ROLE_ADMIN，服务端却判不出该权限，
`/api/**` 的方法级 `@PreAuthorize("hasAuthority('ROLE_ADMIN')")` 一律 403。

修复：自定义 `JwtAuthenticationConverter`，把 `scope`（SCOPE_*）与
`roles`（原样）合并成 authorities，并接入 oauth2ResourceServer。
现有 token 立即生效，无需重新登录。

注意：**不要靠删掉 ROLE_ADMIN 注解来"解决"**——
`AdminApiAuthorizationTest` 会立刻抓到普通用户变成 200 的安全回归。

## 十四、EdgeOne 部署参数陷阱（导致 "Unexpected token '<'"）

现象：前端报 `Unexpected token '<', "<!DOCTYPE "... is not valid JSON`。

排查链路：
1. `admin.civer.cn/api/me` 返回 **200 text/html `<!DOCTYPE`**（EdgeOne Pages 的 SPA 回退）；
2. 该域名上部署的主 JS 是 `index-Clnb6CTa.js`，里面**没有** `https://um.civer.cn`；
3. 说明跑的是旧版前端（`API_BASE` 为空，用相对路径请求），
   fetch `/api/me` 打到前端域名 → 被 SPA fallback 接住返回 index.html → JSON 解析失败。

**根因**：EdgeOne 部署工具的 `workspacePath` 与 `builtFolderPath` 必须指向
**同一个纯产物目录**。有两次把 workspacePath 设成了 `frontend/`，
工具便在该目录下使用/回写 `.edgeone/` 缓存里的旧产物，把新构建覆盖掉了。

正确做法：

```bash
# 1. 干净构建（必须带 VITE_API_BASE，否则前端会用相对路径）
cd client-usermanage/frontend
VITE_API_BASE=https://um.civer.cn \
VITE_AUTH_SERVER_URL=https://idp.civer.cn \
VITE_FRONTEND_URL=https://admin.civer.cn \
node node_modules/vite/bin/vite.js build
cp dist/index.html dist/404.html

# 2. 复制到独立目录，部署时两个参数都指向它
cd ..
rm -rf pages-out && mkdir pages-out && cp -r frontend/dist/. pages-out/
# deploy_folder: builtFolderPath = workspacePath = <abs>/pages-out
```

部署后必须验证：

```bash
curl -s https://admin.civer.cn/ | grep -oE 'assets/index-[A-Za-z0-9_-]+\.js'
curl -s https://admin.civer.cn/<上面那个JS> | grep -o 'https://um.civer.cn'
```

两条都要对得上，否则说明又部署成旧版了。

浏览器若仍加载旧页面，需 Ctrl+Shift+R 硬刷新（index.html 可能被浏览器缓存）。

## 十五、让 EdgeOne 自己构建（方案与步骤，2026-11-03）

问题：现在每次发前端都要本地 `vite build` → 复制 `pages-out/` → 上传，机器换一台就发不了，
产物也不可追溯（线上代码与仓库哪个提交对应，说不清）。

结论：**可以**。EdgeOne Pages 支持「导入 Git 仓库 + 自定义构建」，构建设置里有
根目录 / 构建命令 / 输出目录 / 环境变量 / Node 版本五项，正好够用。
但有一个前提绕不过去：

> **现有的 `aidp-admin-console` 是「直接上传」类型的项目。**
> CLI 与 MCP 的 `deploy_folder` 只能往这种项目推产物；项目类型不能改成 Git 关联。
> 所以要走自动构建，必须**新建一个 Git 类型的项目**，再把 `admin.civer.cn` 迁过去。

### 15.1 建议的构建设置

| 项 | 值 |
|---|---|
| 代码源 | GitHub `Quisperc/AIDP`（`origin` 已存在，无需额外配置）|
| 部署分支 | `main` |
| 根目录 | `client-usermanage/frontend` |
| 构建命令 | `pnpm run build` |
| 输出目录 | `dist` |
| Node 版本 | 22.x（`package.json` 要求 `>=20`）|
| 环境变量 | `VITE_API_BASE=https://um.civer.cn`<br>`VITE_AUTH_SERVER_URL=https://idp.civer.cn`<br>`VITE_FRONTEND_URL=https://admin.civer.cn` |

两个要点：

1. **不要再写 `cp dist/index.html dist/404.html`**。这步已进入 `npm run build`
   （`scripts/postbuild.mjs`），平台构建会自动完成 SPA 路由兜底。
2. 包管理器由平台按 lock 文件自动判定：仓库里有 `pnpm-lock.yaml` → `pnpm install`
   （平台支持 pnpm 6–9）。**不要**改成 `npm install`，会因为没有
   `package-lock.json` 而重新解析依赖，版本可能与本地不一致。

若代码源选 CNB，还要多做一步：CNB 不支持原生 Webhook，需要在 `.cnb.yml`
里配置 EdgeOne 的 webhook 插件，push 后才会触发构建。官方示例见
<https://pages.edgeone.ai/document/importing-a-git-repository>。
用 GitHub 则没这一步。

### 15.2 域名迁移（有几分钟中断，需选低峰）

1. 控制台用上面的设置创建新项目，先在其默认域名上验证：
   首页引用的 `assets/index-*.js` 里必须含 `https://um.civer.cn`，
   `/users` 直接访问要返回 200（说明 404.html 生效）。
2. 旧项目 `aidp-admin-console` → 域名管理 → 解绑 `admin.civer.cn`。
3. 新项目 → 域名管理 → 添加 `admin.civer.cn`，按控制台给出的 CNAME 配置，等证书签发。
4. 迁移完成后旧项目**先别删**，留作回退；确认稳定一周再清。

DNS 记录值以控制台显示的为准，不要沿用旧值（不同项目的 CNAME 目标不同）。

### 15.3 关于「um 和 idp 是不是就不用构建了」

不是同一个层面的问题：

| 站点 | 有没有前端构建 | 现在怎么发 |
|---|---|---|
| `admin.civer.cn` | **有**，唯一的前端产物 | EdgeOne（本轮改为 Git 自动构建）|
| `um.civer.cn` | 没有前端，只有 REST API | Maven 打 jar，CNB `user-v*` 标签触发 |
| `idp.civer.cn` | 没有前端，页面是 Thymeleaf 服务端渲染 | Maven 打 jar，CNB `auth-v*` 标签触发 |

所以「内联就不用构建」只对了前半句：它们确实不产生前端资源，
但 Java 代码或模板一改，仍然要重新打 jar 并重启容器。
两个 jar 的发布继续走现有的 CNB 标签流水线，与 EdgeOne 无关。
