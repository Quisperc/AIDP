# 邮件发送 / 邮箱验证功能评估

> **决策记录 · 2026-11-06**
>
> **结论：不实现邮件发送，也不引入验证码系统或确认链接。**
> 本文档记录判定依据、重开条件与将来实施的规范预案，避免同一个问题被反复提起。
> 本次只落地文末「七」列出的三项零成本改进，未新增任何邮件基础设施。

---

## 一、结论与适用范围

需求原话是「新增邮件发送功能，用来校验用户填入的邮箱是否有效」。
本系统（AIDP 统一认证中心）当前**没有强烈必要**做这件事，因此按「无强烈必要即否定」的原则关闭。

适用范围：内部统一认证中心 `idp.civer.cn`，账号由组织统一分配、管理台由 `ROLE_ADMIN` 创建，
没有公网自助注册；下游是同一主域下的内部子系统。

---

## 二、先把「邮箱有效性」拆成三层

发邮件只能覆盖其中一层，需求本身存在目标与手段的错位。

| 层级 | 含义 | 发邮件能否证明 | 本系统现状 |
|---|---|---|---|
| L1 语法合法 | 值符合 RFC 5322 `addr-spec` | 不需要发邮件，本地校验即可 | **已覆盖**（见「七」第 2 点，改为标准 `@Email`） |
| L2 地址真实存在 / 可收信 | 域名有 MX、收件人确实存在 | **不能可靠证明**：SMTP `VRFY` / `EXPN` 几乎被所有服务商禁用，`RCPT TO` 探测会被灰名单与反垃圾策略污染；发信成功也不等于送达 | 未做，也不必做 |
| L3 归属权 | 该用户确实控制这个邮箱 | **能**，且只有这一层能；须由用户完成一次带外挑战 | 未做，当前也不需要 |

也就是说：**邮件验证不是「校验邮箱有效性」，而是「证明邮箱归属权」**。
如果诉求只是「别让用户填一串乱码」，本地格式校验就够了；
如果诉求是「这个邮箱必须属于本人」，那才需要发邮件——而本系统不需要这个证明。

## 三、必要性判定：基于本仓库现状

### 3.1 邮箱在系统里承担什么角色

逐条核对代码，邮箱**不承担任何安全敏感职责**：

| 可能的用途 | 现状 | 证据 |
|---|---|---|
| 登录标识 | 否，登录名是 `username` | `User.java`、`CustomUserDetailsService` |
| 密码找回通道 | 否，走管理员重置 | `templates/login.html`「忘记密码请联系系统管理员重置」；`LastAdminGuardTest` |
| 账号合并 / 唯一键 | 否，按 `(iss, sub)` 关联 | `docs/接入规范.md` 自检清单；OIDC Core §5.7 |
| MFA / 安全告警 / 审计送达 | 否，无任何发信场景 | `application.yml` 无 SMTP 配置，`pom.xml` 无 mail starter |
| 公网自助注册 | 否，账号组织分配 | `README.md`、`AdminUserController` |

它只是 OIDC `email` scope 下的一个**展示型 claim**。填错的唯一后果是下游联系方式不准确。

### 3.2 风险已经被正确的机制兜住

- `User.email` / `User.emailVerified`（V3 迁移）已存在。
- `AccountService`：用户自助填写 → `emailVerified=false`，改邮箱自动重置为 `false`。
- `UserAdminService`：管理员录入 → `emailVerified=true`。
- `TokenConfig`：仅在请求 `email` scope 时下发 `email` / `email_verified`，
  注释明确「自助填写的邮箱未经验证，绝不能声明为已验证：下游若拿 `email_verified` 做账号合并会造成账号接管」。
- `docs/接入规范.md`：已要求下游「检查 `email_verified` 后再使用」。

这正是 **OIDC Core 1.0 §5.1** 的标准语义：`email_verified=true` 表示 OP 采取了
*affirmative steps* 确认用户当时控制该邮箱，而「验证方式由信任框架或合同约定决定」
（原文：*The means by which an e-mail address is verified is context specific, and dependent
upon the trust framework or contractual agreements*）。
**管理员录入 = 组织内部信任框架**，对内部系统是合规且成本最低的验证方式。

### 3.3 成本收益与两个反直觉风险

收益只是把一个布尔位从 `false` 翻成 `true`，而当前没有任何下游依赖这个 `true` 做决策。
成本却是新增一整套基础设施：SMTP 凭据与邮件网关、发信域名信誉、Token 存储与过期、
重发限频、邮件模板、Flyway 迁移、本地/CI 的假 SMTP、测试补充、部署 SOP 与送达监控。

两个容易被忽略的反向风险：

1. **抬高下游对邮箱的信任**：一旦有了「已验证邮箱」，下游很可能把它当可信身份依据去做账号合并。
   而 NIST SP 800-63B-4 明确**不允许把 email 用作带外认证器**（out-of-band authenticator）——
   邮箱本身常是身份链路里最弱的一环。加了功能反而可能扩大账号接管面。
2. **合规成本**：邮箱属个人信息，交给第三方邮件服务商属于对外提供，
   在《个人信息保护法》最小必要原则与 GB/T 35273 下要补告知同意、更新隐私政策并留存记录。

## 四、什么时候必须重开这个议题

以下任一条成立，才需要重新评估并实施邮件验证；当前 5 条全部不成立。

1. 开通**自助找回密码**（邮箱成为恢复通道，不验证归属权等于把重置链接发给任意填写者）。
2. 开放**公网自助注册**，或把邮箱作为登录名 / 账号去重键。
3. 下游开始用 `email_verified=true` 做**账号合并、授权提升、资金或敏感操作**。
4. 邮箱用于接收**安全告警、MFA、审计送达**。
5. 合同 / 合规要求**通知必须能送达本人**。

## 五、若将来实施：技术方案预案（本次不实现）

### 5.1 验证码 vs 确认链接

| 维度 | 验证码 OTP | 签名确认链接 |
|---|---|---|
| 交互 | 用户留在页面输入，需输入页与倒计时 | 去邮箱点一下，异步完成 |
| 服务端状态 | 哈希存储 + 尝试计数 + 重发限频 + 枚举防护 | 无状态签名 Token + 一次性消费标记 |
| 本项目适配 | Thymeleaf SSR 下要新增表单、限频组件，改动更大 | 一个 GET 端点即可，最省 |
| 主要风险 | 暴力破解、邮件轰炸、账号枚举 | Referer 泄露、Host 头注入、Token 重放 |

**选签名链接。** 它直接对应 OIDC Core §5.1 的 *affirmative steps*，
且与「单 jar、单域名、无前端工程」的架构最契合。

### 5.2 最小实现骨架

- Token：HMAC 签名或 JWT，claims 至少含 `sub=public_id`、`email`、`purpose=email_verify`、
  `jti`、`iat`、`exp`（建议 ≤ 30 分钟）；库里存 `jti` 消费标记或 `email_verified_at` 防重放。
- 端点：`POST /account/email/verify-request`（需已登录 + 按账号/IP 限频）、
  `GET /account/email/verify?token=...`（不需要登录态）。
- 状态机：只有当前 `email` 与 Token 内一致时才置 `email_verified=true`；
  改邮箱自动置 `false`（现有逻辑已如此）；成功后其余未消费 Token 全部作废。
- 响应：请求发送一律返回同一句提示，不区分「邮箱是否存在」，防账号枚举。

### 5.3 dev / prod 差异

| | dev | prod |
|---|---|---|
| 发信 | GreenMail / MailHog 假 SMTP，验收邮件内容而不真发 | 企业邮件网关或可信 ESP，独立发信子域 |
| 域名信誉 | 不关心 | SPF / DKIM / DMARC 全配，监控退信率与投诉率 |
| 凭据 | 本地环境变量 | 密钥管理，禁止进仓库与镜像 |
| 监控 | 控制台日志 | 发送成功率、队列积压、验证转化率告警 |

### 5.4 风险与常见坑

- **Host 头注入**：确认链接的域名必须硬编码或白名单校验，不能取 `Host` 头，
  否则攻击者可构造指向自己域名的验证链接。
- **Referer 泄露**：确认页设 `Referrer-Policy: no-referrer`，页面不引用第三方资源。
- **Token 泄露与重放**：不写进应用日志、不进 URL 片段以外的第三方请求、单次失效、短时效。
- **送达**：没配 SPF/DKIM/DMARC 时验证邮件几乎必进垃圾箱，会让功能看起来「坏了」。
- **滥用**：重发与按目标地址限频，否则成为邮件轰炸放大器。
- **存量迁移**：新增 Token 表要走 Flyway 新版本。V3 曾清空全部
  `oauth2_authorization` / `oauth2_authorization_consent` 导致全员重登重授权，
  同类改动必须先评估存量影响。
- **回滚**：Flyway 不可降级，回滚前先确认新迁移对旧代码是否可容忍（加列通常可，改列不行）。

## 六、遵循的标准规范

| 规范 | 本决策 / 预案中的用途 |
|---|---|
| OIDC Core 1.0 §5.1 | `email` 值须符合 RFC 5322 `addr-spec`；`email_verified` 语义与「信任框架决定验证方式」 |
| OIDC Core 1.0 §5.7 | RP 不得依赖 `email` / `preferred_username` 的唯一性与稳定性，按 `(iss, sub)` 关联 |
| RFC 5322 §3.4.1 / RFC 5321 | `addr-spec` 语法；不依赖 `VRFY` 判断地址存在 |
| RFC 6531 (EAI) | 国际化邮箱，按业务需要决定是否支持 |
| OWASP *Forgot Password Cheat Sheet*（URL Tokens / PINs） | CSPRNG、绑定用户、单次失效、限时、安全存储；URL 不取 Host 头、强制 HTTPS、`Referrer-Policy: no-referrer`、限频、统一响应防枚举 |
| OWASP ASVS V6.4 | 认证因子生命周期与恢复（以官方最新版章节号为准） |
| NIST SP 800-63B-4 §3.1.3.2 / §3.2.9 | ≥ 6 位或等效熵、10 分钟内完成、只接受一次、CSPRNG；< 64 bit 必须限频且换新码不重置失败计数；受限认证器；email 不得用于带外认证 |
| RFC 7208 / 6376 / 7489 | SPF / DKIM / DMARC，发信送达侧 |
| RFC 8058 | 一键退订（仅当发送营销 / 通知类邮件时） |
| 《个人信息保护法》、GB/T 35273 | 最小必要、告知同意、个人信息对外提供 |

## 七、本次实际落地（不引入邮件发送）

按「比发邮件更值得做的三件小事」执行，均为防御性改进：

1. **邮箱大小写归一化缺陷**：新增 `EmailPolicy.normalize`（trim + `Locale.ROOT` 小写），
   `AccountService` 与 `UserAdminService` 两条写入路径共用；`UserRepository` 改为
   `findByEmailIgnoreCase`；新增 Flyway `V4__normalize_user_email.sql` 规整存量并处理冲突。
   原先 `A@x.com` 与 `a@x.com` 可同时落库且互不查到，绕过邮箱唯一性约束。
2. **标准格式校验**：引入 `spring-boot-starter-validation`，用 Jakarta `@Email`
   替换自写正则；管理台路径原先只查重、不校验格式，一并补齐。
3. **下游义务写清楚**：`docs/接入规范.md` 新增「email claim 的使用约束」章节，
   明确 `true` 来自管理员录入的组织信任框架而非技术验证，未验证邮箱不得用于
   账号合并、授权提升、密码重置、敏感通知；`docs/外部系统接入.md` 同步补注。

## 八、部署注意事项

- V4 是**数据规整**，不改表结构、不清空授权，不需要用户重新登录或重新同意。
- 上线前建议先在库上执行下面语句排查历史脏数据（应返回 0 行）：

  ```sql
  SELECT lower(email) AS dup, count(*) FROM users
   WHERE email IS NOT NULL GROUP BY lower(email) HAVING count(*) > 1;
  ```

- 若存在重复，V4 会保留 `id` 最小的一行、把其余行的邮箱清空并重置
  `email_verified`，发布后通知相关账号重新填写资料即可。
- Flyway 迁移失败会中止启动（项目既有约定），不会带着半截数据继续跑。
- 回滚：V4 只改 `users.email` 的字母大小写与重复行，旧版本 jar 可正常读取，无需 repair。
