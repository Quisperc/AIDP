# AIDP 系统优化方案

> 审查对象：`github.com/Quisperc/AIDP`（Spring Boot 4.0.3 / Java 22 / OIDC SSO）
> 规模：72 个文件 · Java ~2650 行 · HTML ~4300 行 · 零测试
> 结论：**有优化空间，且空间很大。存在一个必须立刻修的 P0 级权限漏洞。**

---

## 一、体检结论速览

| 维度 | 现状 | 评级 |
|---|---|---|
| 安全性 | 存在 1 个 P0 权限绕过 + 1 个 P0 开放重定向 | 🔴 高危 |
| 架构可扩展性 | RSA 密钥内存随机生成，无法水平扩容 | 🔴 高危 |

## 二、P0 —— 必须立刻修（本周内）

### 2.1 权限注解全部静默失效 🔴

**这是本次审查最严重的问题。**

`AuthServerApplication.java` 只有 `@SpringBootApplication` + `@EnableJpaRepositories`，**缺少 `@EnableMethodSecurity`**：

```java
@SpringBootApplication
@EnableJpaRepositories(basePackages = "cn.civer.authserver.repository")
// ❌ 没有 @EnableMethodSecurity
public class AuthServerApplication { ... }
```

Spring Security 6/7 **默认不启用方法级安全**。因此 auth-server 中所有 `@PreAuthorize` 全部**静默失效、无任何报错**：

- `RegisteredClientController`（类级 `@PreAuthorize("hasAuthority('ROLE_ADMIN')")`）→ `/api/clients` 全部增删改查
- `UserManagementController`（方法级）→ `/api/users` 全部增删改查

而 `AuthorizationServerConfig` 对 `/api/**` 只要求 `SCOPE_openid`——**任何登录用户都有 openid scope**。

**实际后果**：任意一个 `ROLE_USER` 普通用户，拿到自己的 access token 后就能：
- `POST /api/users` 创建 ROLE_ADMIN 管理员账号
- `PUT /api/users/{id}` 改任意用户密码
- `DELETE /api/clients/{id}` 删除任意客户端

对照：client-usermanage 的 `ClientApplication` **有** `@EnableMethodSecurity`，所以客户端侧是正常的。只有 auth-server 漏了。

**修复**（一行）：

```java
@SpringBootApplication
@EnableJpaRepositories(basePackages = "cn.civer.authserver.repository")
@EnableMethodSecurity   // ✅ 加上
public class AuthServerApplication { ... }
```

> ⚠️ 加上后权限会"突然生效"，需同步确认 admin 账号的 `roles` claim 能正确进入 JWT（`TokenConfig.jwtTokenCustomizer` 已写入 `roles`，链路是通的）。建议先在测试环境验证再用灰度发布。

### 2.2 开放重定向漏洞 🔴

`RevocationController.java:58`：

```java
return "redirect:" + redirectUri;   // ❌ 零校验
```

`redirectUri` 直接来自请求参数，攻击者可构造：

```
/oauth2/revoke-consent?client_id=x&redirect_uri=https://evil.com
```

——一个挂着自家域名的 SSO 跳转，用于钓鱼，可信度极高。

**修复**：复用项目里已有的 `SsoLogoutService.isAllowedLogoutRedirect()`（它的 host 白名单逻辑是对的，只是有性能问题，见 4.3）：

```java
@GetMapping("/oauth2/revoke-consent")
public String revokeConsent(Principal principal,
        @RequestParam("client_id") String clientId,
        @RequestParam(value = "redirect_uri", defaultValue = "/") String redirectUri) {
    // ... 原有 revoke 逻辑 ...
    String safe = ssoLogoutService.isAllowedLogoutRedirect(redirectUri) ? redirectUri : "/";
    return "redirect:" + safe;
}
```

## 三、P1 —— 高优先级（2 周内）

### 3.1 硬编码凭据

| 位置 | 问题 |
|---|---|
| `DataInitializer.java:35-36` | 硬编码创建 `admin/password`、`user/password` |
| `application.yml`（两侧） | `client-secret: secret` 明文 |
| `application.yml` | 数据库 `username/password` 占位符 |

**方案**：默认账号改为"首次启动强制改密"或仅当 `app.bootstrap.enabled=true` 时创建；secret 全部走环境变量；引入 `.env.example`。

### 3.2 User 实体用 lombok `@Data` 🔴

```java
@Entity
@Data          // ❌ 生成的 toString() 会把 password 明文打进日志
public class User { private String password; ... }
```

`@JsonProperty(WRITE_ONLY)` 只管 Jackson 序列化，**管不住 lombok 的 `toString()`**。任何一处 `log.info("user={}", user)` 都会泄露密码哈希。

**方案**：改用 `@Getter @Setter`，并彻底**禁止 Entity 直接作为 API 响应**（现状 `UserManagementController` 直接 `return List<User>`）。抽 `UserResponse` record，密码字段物理不存在。

### 3.3 RSA 密钥每次启动随机生成 → 无法水平扩容

`TokenConfig.java:29-39`：内存 `KeyPairGenerator` 生成，`ImmutableJWKSet` 持有。

**两个后果**：
1. 每次重启，所有已签发 token 全部验签失败 → 生产重启 = 全员掉线
2. 多实例部署时各实例密钥不同 → JWT 校验必然失败 → **架构上锁死单实例**

**方案**（三选一，推荐 B）：
- A. 密钥落库/落盘，启动时加载，无则生成并持久化
- **B. 用 Spring Boot 4 的 `KeyStoreKeyFactory` 或外部挂载 JWK（`spring.security.oauth2.authorizationserver.jwk-set-uri` 指向统一密钥服务）**
- C. 接入 KMS / Vault

### 3.4 Schema 双轨 + 缺索引 + 零事务

- `schema.sql`（OAuth2 三张表）+ `ddl-auto: update`（users 表）→ 两套 schema 管理机制
- `oauth2_authorization.principal_name`、`registered_client_id` 无索引，而 `SsoLogoutService` 每次登出都全表扫
- `RegisteredClientController.deleteClient` 三条 `DELETE` 无 `@Transactional` → 部分失败留脏数据
- 全项目**零 `@Transactional`**、**零测试类**

**方案**：统一 Flyway 管理全部 DDL（关掉 `ddl-auto`），补索引，删除方法加事务，补核心链路集成测试。

## 四、精简优化 —— 可量化的收益

### 4.1 抽取公共 SSO Client Starter（立竿见影）

现状：两个客户端各写一份，逐行对比重复度极高。

| 文件 | client-template | client-usermanage | 差异 |
|---|---|---|---|
| `SecurityConfig.java` | 148 行 | 171 行 | **仅** `/admin/**` 规则 + `successHandler` 两处 |
| `SsoLogoutController.java` | 86 行 | 112 行 | 仅多了 issuer 兜底解析 |

`filterChain`、`getAuthServerIssuerUri`、`onOAuth2LoginFailure`、`isClientConfigError`、`oidcUserService`、`sessionRegistry` **完全一致，逐字符相同**。

**方案**：新建 `sso-client-starter` 模块，通过条件装配开放扩展点：

```java
public interface SsoSecurityCustomizer {
    void customize(HttpSecurity http, AuthorizeHttpRequestsConfigurer<...>.AuthorizationManagerRequestMatcherRegistry authz);
}
```

客户端侧只需：

```java
@Bean
public SsoSecurityCustomizer customizer() {
    return authz -> authz.requestMatchers("/admin/**").hasAuthority("ROLE_ADMIN");
}
```

**收益**：319 + 198 = 517 行 → 公共模块 ~150 行 + 两侧各 ~25 行配置 ≈ 200 行，**净减 ~320 行**，且今后新增子系统接入成本从"复制粘贴 400 行"降到"引一个 starter + 写 3 行"。

### 4.2 建立聚合 Parent POM

现状：三个模块各自 `<parent>spring-boot-starter-parent:4.0.3</parent>`，版本号、Java 22、插件配置三份重复，且：
- 主 pom 引了 `spring-cloud-dependencies` BOM **但没用任何 cloud 组件** → 白白拖慢依赖解析
- client-template 显式声明 `spring-security-oauth2-client`，而 `spring-boot-starter-oauth2-client` 已传递包含 → 冗余

**方案**：`aidp-parent` 聚合三模块，统一 dependencyManagement，删掉 spring-cloud BOM 和冗余显式依赖。

### 4.3 清理代码异味

| 项 | 数量 | 处理 |
|---|---|---|
| `System.out/err.println` | **36 处** | 全部改 SLF4J（涉及 7 个文件） |
| 行内全限定类名 | **353 处** | 补 import（`SsoLogoutService` 191 行里满屏 `java.util.Map`、`org.springframework.security...`，可读性极差） |
| 硬编码 `Duration.ofMinutes(30)` | 3 处 | 提为 `app.token.access-token-ttl` 配置项 |
| DTO 用 public 字段 | 4 个类 | Java 22 直接用 `record`；且 `ClientDto`/`ClientSummaryDto` 在 auth-server 和 client-usermanage **各定义一份**，抽到 starter |
| `catch (Throwable t)` | 1 处 | `SsoLogoutSuccessHandler` 捕获 Throwable 吞掉 Error，改 `catch (Exception)` |
| 死代码 | 若干 | `ConsentController.previouslyApprovedScopes` 永远为空 Set；`DataInitializer` 的 `var existing` 定义了没用 |

### 4.4 性能热点

1. **`SsoLogoutService.isAllowedLogoutRedirect()`** —— 每次调用 `SELECT redirect_uris FROM oauth2_registered_client` 全表扫描并重新解析构建 host Set。登出是高频操作。**方案**：缓存 host 白名单，客户端变更时失效。
2. **`broadcastBackchannelLogout()`** —— 每次登出 `HttpClient.newHttpClient()` 新建客户端，**无超时、无连接池**。`sendAsync` 且 `exceptionally` 只打日志，遇到对端不响应会长期挂起线程。**方案**：注入单例 `HttpClient` + `connectTimeout(Duration.ofSeconds(3))` + `executor(线程池)`。
3. **`UserService.getUser(Long id)`** —— `getUsers().stream().filter(...)`，查单个用户要**拉全表**。**方案**：补 `GET /api/users/{id}` 端点（现有 `UserServiceClient` 缺这个）。
4. **每个 logout 请求新建 `NimbusJwtEncoder`** —— 应注入复用。

## 五、前端能否独立优化？—— 先纠正一个前提

### 5.1 现状：这里没有"前端工程"

```
无 package.json · 无构建产物 · 无独立 .css/.js 文件 · 无 CDN 资源
```
15 个 Thymeleaf 模板，**全部样式内联在各自的 `<style>` 块里**。所以严格说，现在谈"前端独立优化"是谈**如何把散落的样式资产收敛成可维护的层**，而不是拆出一个 SPA。

### 5.2 硬数据

| 指标 | 数值 |
|---|---|
| 内联 CSS 总行数 | **2879 行** |
| 全局去重后 | **694 行** |
| **重复率** | **75.9%** |
| 加载 Google Fonts 的页面 | **14 / 15** |
| 含 `@keyframes` + `backdrop-filter` 的页面 | **15 / 15** |

单页内联 CSS 最多的是 `clients.html`（296 行）和 `users.html`（282 行）。

### 5.3 三个具体病灶

**① 样式零复用，且无法被浏览器缓存**
每个页面整页刷新都要重传约 200 行 CSS。15 个页面互相之间重复 75.9%，等于每次都在重复传输同样的字节。

**② Google Fonts 是国内部署的真实性能杀手**
```html
<link href="https://fonts.googleapis.com/css2?family=Inter:wght@300;400;500;600;700&display=swap" rel="stylesheet">
```
14 个页面全部阻塞式加载。国内网络环境下这个请求会超时挂起，**直接拖垮首屏**。这是当前最容易被感知到的性能问题。

**③ `nav.html` fragment 自带 154 行 CSS**
每个引用它的页面都会把这段 CSS 再注入一次，重复叠加。

### 5.4 好消息：设计语言其实是统一的

配色统计显示只有两套主色，说明设计是有意识的，只是没落到 token 上：

| 用途 | 色值 | 出现次数 |
|---|---|---|
| 按钮/强调渐变 | `#667eea → #764ba2` | 20 |
| 页面背景渐变 | `#0f0c29 → #302b63` | 14 |
| 点缀色 | `#f093fb → #f5576c` | 7 |
| 成功色 | `#11998e → #38ef7d` | 5 |

**这意味着抽取成本很低——不需要重新设计，只需要把已存在的设计决策固化成变量。**

### 5.5 推荐方案：分层收敛（保守路线）

不建议贸然 SPA 化。原因：**授权服务器的登录页和授权同意页按 OAuth2 规范必须服务端渲染**，这是用户代理交互的一部分，SPA 化会引入额外复杂度和安全风险。

**第一阶段（1 周，风险极低，收益立竿见影）**

```
src/main/resources/static/
├── css/tokens.css      ← 设计变量（颜色/间距/圆角/字号）
├── css/base.css        ← reset + 排版 + 布局骨架
├── css/components.css  ← 卡片 / 按钮 / 表单 / 表格 / 页脚
└── css/pages/*.css     ← 各页面只留真正特有的样式
```

1. 把 694 行去重后的 CSS 拆成 `tokens / base / components` 三层，各模板改为 `<link rel="stylesheet">` 外链
2. **移除全部 Google Fonts 外链**，改用系统字体栈：
   ```css
   font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI',
                'PingFang SC', 'Hiragino Sans GB', 'Microsoft YaHei', sans-serif;
   ```
   （这行改动单独就能解决国内首屏问题）
3. `nav.html` / `footer.html` 的 CSS 一并外链，不再随 fragment 重复注入
4. 各页面保留 `<style>` 只写特有样式

**预期收益**：2879 行 → 约 800 行（公共 694 + 各页特有 ~100），**减 72%**；CSS 从"每页重传"变成"一次缓存，全站复用"；首屏不再被 Google Fonts 阻塞。

**第二阶段（可选）**

- 引入 `th:fragment` / `th:replace` 布局方言做模板继承，消除页面间 HTML 结构重复
- 14 处 `@keyframes` + `backdrop-filter` 收敛成 2-3 个可复用组件，并在移动端降级（`@media (prefers-reduced-motion)`）
- 若确需 SPA：只对 **client-usermanage 管理后台**做前后端分离（Vue 3 + Vite），auth-server 的登录/同意页保持服务端渲染

### 5.6 前端优化为什么可以"独立"进行

关键判断：**第一阶段的改动完全不触碰 Java 代码**。

```
只改：  <style>...</style>  →  <link rel="stylesheet" th:href="@{/css/components.css}">
不动：  Controller / Service / SecurityConfig / 任何 Java 文件
```

Thymeleaf 的 `th:href="@{/css/...}"` 会自动处理 context path。可以作为一个**独立的 PR 提交和回滚**，风险可控——这正是它适合优先做的原因。

## 七、一句话总结

系统**功能完整、设计意图清晰**（OIDC 授权码 + PKCE + Back-Channel Logout 的主链路是对的），问题集中在**工程化收敛不足**和**两个被静默忽略的安全点**。

最需要立刻动手的两件事：
1. **`AuthServerApplication` 加一行 `@EnableMethodSecurity`** —— 现在任何登录用户都能改任何人的密码
2. **把 2879 行内联 CSS 抽成外链、砍掉 Google Fonts** —— 两天的活，减 72% 样式代码，且不动一行 Java
